## 2a. Reminder lifecycle, scheduler design, and notification policy (Phase 3 batch 3)

**Due-date interaction policy** (the batch brief asked for explicit, predictable rules — no ambiguous edge cases):

| Event | Effect on an existing reminder |
|---|---|
| Task's due date changes | **Unchanged.** A reminder is always an absolute UTC instant, fixed at set-time — editing the due date never silently moves a reminder the user already confirmed. (If it was set "N days before due", that offset was resolved into a fixed instant once, at creation/edit time, and is not recomputed.) |
| Task completed | The pending (undelivered) reminder is **deleted**, not just skipped. Completion is a deliberate, usually-permanent state — nobody needs reminding about a done task. |
| Task reopened | **Not restored.** The reminder is gone (see above); the user re-adds one if they still want it. Predictable over clever: resurrecting a stale reminder on reopen would be a surprise. |
| Task soft-deleted | **Kept**, but the delivery engine's live query (`task.deletedAt: null`) skips it while deleted. Unlike completion, soft-delete is an accidental-action safety net (the undo banner), so losing the reminder to a delete-then-undo click would be the more surprising outcome. |
| Task restored | The kept reminder becomes eligible again. If it elapsed during the (normally brief) deleted window, it fires on the next cron tick — accepted as a rare, benign edge case given how short that window usually is. |
| Reminder edited (including after it already fired) | Replaces the single row for that (task, viewer) pair and resets `delivered_at` to null, so it becomes live again at the new time — "edit" most plausibly means "remind me again, at this new time." |
| `remind_at` is already in the past when set | **Allowed, not rejected.** The next cron tick delivers it almost immediately — useful for "remind me in 5 minutes," and simpler than adding a validation rule nothing asked for. |

**Watcher/assignee notification policy** — which task events actually notify people, and which don't (the brief asked for "do not spam… use a documented event-to-notification policy"):

- **Recipients** for every watcher-policy event: task owner + assignees + watchers, deduped into one set, **actor always excluded** (`taskNotifiableRecipients()` in `tasks/server/access.ts`, shared by every call site below so the computation happens exactly once, consistently).
- **Notifies:** status changes (`TASK_STATUS_CHANGED` — covers both `setTaskCompletion`'s complete/reopen and `updateTask`'s other status transitions), due-date changes (`TASK_DUE_DATE_CHANGED`), new comments (`TASK_COMMENTED`, deduped against anyone already getting a `MENTIONED` ping for that same comment), a dependency's last open blocker completing (`TASK_UNBLOCKED` — the one dependency event judged to carry real value; "a dependency was added" does not notify anyone).
- **Does not notify:** title/description/priority/estimate/someday/project-move edits (still recorded as a plain `updated` activity, just no notification — editing a task shouldn't spam its watchers over every minor field), a dependency being *added* (only *resolving* one is notable).
- **Dedupe keys** for the three new event-driven types include the task's post-mutation `version` (`task:{id}:v{version}:status:{userId}`, etc.) so each genuinely new event gets its own notification while an accidental duplicate call for the *same* mutation attempt still collapses to one row, same mechanism `TASK_ASSIGNED` already relied on.
- `TASK_OVERDUE` stays unused, same as before this batch — a "daily digest of overdue tasks" is a Phase 6 (attention centre) concern, not something this batch's per-event model fits naturally.

**Reminder delivery engine** (`src/features/reminders/server/engine.ts`, called from `src/app/api/cron/reminders/route.ts`):

1. Reads up to 100 reminders where `delivered_at IS NULL AND remind_at <= now()`, joined to a live check that the task is not deleted and not `DONE`/`CANCELLED` — this re-evaluates *current* state at delivery time, not whatever was true when the reminder was set, per the brief's requirement.
2. For a workspace-scoped task, also checks the recipient still has an **ACTIVE** membership in that workspace before notifying (skips and marks delivered, never notifies, if they've left) — the one additional "inaccessible user" check added on top of the live task-state filter, since losing workspace access is the realistic way a reminder's recipient stops being allowed to see it.
3. For each candidate, claims it with `UPDATE reminders SET delivered_at = now() WHERE id = ? AND delivered_at IS NULL` **inside the same transaction** as the `notify()` insert. Two workers racing the same row: Postgres serializes the two `UPDATE`s, so exactly one affects a row; the other affects zero and skips notifying — no duplicate delivery, no `FOR UPDATE SKIP LOCKED` or other explicit lock needed for this scale. If `notify()` throws, the whole transaction (claim included) rolls back, so the reminder stays undelivered and is retried next tick — "safe retry" falls out of the transaction boundary for free.
4. The notification's `dedupeKey` includes the reminder's `updated_at` timestamp, not just its id — because editing a reminder after it already fired resets `delivered_at` (see the policy table above), and without `updated_at` in the key the second delivery's `notify()` call would collide with the first one's now-reused dedupe key and silently no-op.

**Why a narrow scheduler, not the Phase 4 `Job` table:** `docs/ARCHITECTURE.md`'s "Background jobs (planned, Phase 4)" section already designs a generic `Job` table (`run_at`, `dedupe_key`, attempts, status) for SLA breaches, habit prompts, subscription charges, automations, AI jobs and email delivery — reminders were explicitly listed as one future consumer of it. This batch's brief asked to use "the smallest appropriate architecture" and not build a queue system prematurely, so reminders got their own tight `Reminder` table + cron route instead of standing up the generic table for its first and only caller. This also happens to resolve Q-PO-13 ("background-job runtime on Vercel: Cron + DB queue, or an external queue") **for this one use case** — Vercel Cron + an idempotent DB-claim — without closing the broader question for Phase 4's other consumers, which may still want the fuller `Job` abstraction once there's more than one kind of scheduled work to generalize over.

**Vercel configuration required** (also see §8 below):
- `vercel.json` now has a `crons` entry: `{"path": "/api/cron/reminders", "schedule": "*/5 * * * *"}`. **Vercel's Hobby plan limits cron jobs to once per day** — if the product owner is on Hobby, this schedule will silently run far less often than every 5 minutes; either upgrade to Pro or accept daily reminder delivery until then.
- Set a `CRON_SECRET` environment variable in the Vercel project. When set, the route requires `Authorization: Bearer <CRON_SECRET>` — which Vercel's own Cron trigger sends automatically once the env var exists, so no other wiring is needed. Left unset locally on purpose (`npm run dev`/tests call the route with no auth header and it's allowed through), so don't set it in local `.env`.

## 2b. Filters, bulk actions, and ordering (Phase 3 batch 4)

**Filter state model:** URL search params, server-parsed — the same mechanism `?scope=`/`?task=`/`?deleted=` already used in `src/app/(app)/planner/[view]/page.tsx`, extended rather than replaced. `parsePlannerFilters(sp)` (`features/tasks/server/filters.ts`) turns `?priority=URGENT,HIGH&label=id1,id2&overdue=1…` into a typed `PlannerFilters` object; every id-valued dimension (assignee/creator/label/project) is validated only for *shape* (looks like a cuid), never for the viewer's access — because every fragment `plannerFiltersWhere` builds is ANDed with the existing `visibleTasksWhere`, a bogus or inaccessible id can only narrow a query to nothing extra, never expose anything new. No client-side filter state beyond the popover's own open/closed `<details>`; every control writes straight to the URL on change via the same `URLSearchParams`-cloning idiom `task-row.tsx` already used for `?task=`.

**Ownership-scoping bug found and fixed during this batch's own integration tests:** `delegated`/`watched` cannot be ANDed on top of a non-Delegated view's default "mine" scoping (`mineWhere`) — `mineWhere` and `delegatedWhere` are mutually exclusive by construction (delegated requires having assignees I'm *not* one of; mine requires the opposite), so "today + delegated" would silently always return zero rows. Fixed by having those two filters *replace* the view's ownership fragment instead of narrowing it (`resolveOwnership` in `filters.ts`): `watched` wins if both are somehow set. `ownershipWhere` (the view's own default, ignoring any filter) stays separately exported for `getPlannerCounts`'s nav-badge counts, which intentionally stay unfiltered.

**Bulk-mutation semantics — best-effort/partial, not atomic:** every function in `features/tasks/server/bulk.ts` loads the requested task ids via a new batched `findVisibleTasks`, partitions them into "allowed" (passes `canEditTask`/`canDeleteTask` individually) and "skipped," and only ever mutates the allowed subset — one shared task a caller can't touch never blocks the rest of a broad multi-select. Every function returns `{updatedIds, skippedIds}`, and the `BulkToolbar` UI surfaces a literal "Updated N · skipped M (no permission)" message rather than pretending every selected task was touched. Each function opens exactly **one** `db.$transaction` for its whole allowed batch (not one per task); where a mutation's side effects are complex enough to risk duplicating business rules (recurrence regeneration, reminder-clearing, dependency-unblock notifications on completion), the existing single-task service logic was refactored to expose a reusable `tx`-scoped core (`completeTaskCore` in `tasks/server/service.ts`) that both the single-task action and the bulk one call — not two implementations of "what happens when a task completes." Bulk mutations are **not** version-guarded (no optimistic-concurrency check against `task.version`), matching the precedent `setTaskAssignees`/`setTaskLabels` already set for relation-changing operations — requiring an exact version match across an entire multi-select would make bulk actions fail constantly in any workspace with concurrent edits. Label/assignee bulk ops are genuinely additive/subtractive (`bulkAddLabels`/`bulkRemoveLabels`, `bulkAddAssignees`/`bulkRemoveAssignees`) — a deliberately different shape from single-task `setTaskLabels`/`setTaskAssignees`'s "replace the whole set," since "add this label to 40 tasks" must never silently strip each task's other labels.

**Bulk notifications collapse per recipient, never duplicate, never spam beyond what the existing policy already allows:** `src/server/notify-bulk.ts`'s `BulkNotifyAccumulator` collects every `(recipient, event type, task)` candidate a bulk action's per-task logic would have generated (the exact same calls `updateTask`/`setTaskCompletion`/`setTaskAssignees` already make for a single task), then flushes once per bulk call, inside the same transaction: a recipient touched by exactly one task in the batch gets the **identical, unchanged single-task notification** (same type, same deep link); a recipient touched by more than one gets **exactly one** aggregated notification instead, using one of 4 new additive `NotificationType` values (`TASK_STATUS_CHANGED_BULK`, `TASK_DUE_DATE_CHANGED_BULK`, `TASK_ASSIGNED_BULK`, `TASK_UNBLOCKED_BULK`) with a new `Notification.data` JSON column carrying `{count, taskIds}` (capped at 50 ids). Never both the individual and the aggregated form for the same recipient/event. This is intentionally *not* new spam-suppression logic layered on top of the existing policy — bulk label/priority/move mutations still notify nobody, exactly as their single-task equivalents don't, because the accumulator only ever receives the same candidates the existing watcher policy already produces. Verified by `batch4.integration.test.ts`'s "bulk notification invariants" block (6 explicit cases: single-task → single type; bulk-of-one → identical to single-task; bulk-of-many → one aggregated row per recipient/type; no duplicates; actor always excluded; a user without visibility is never notified).

**Ordering model:** reuses `Task.sortOrder` (`Float`, already in the schema, already written by recurrence-copy and already driving project-list order — no new column). `reorderTask(viewer, taskId, {beforeId, afterId})` computes the new rank **entirely server-side, inside one transaction** — the client (`TaskListWithSelection`'s optimistic reorder) only ever sends the two visible neighbor ids, never a computed value. `domain/ranking.ts`'s `rankBetween`/`needsRebalance`/`reseedRun` are pure math, never touch the database and are never evaluated client-side. On a rank collision (`needsRebalance` true — the common case is several siblings still at the Float column's `0` default, though in practice `createTask` seeds new rows with `Date.now()`, so true collisions are rarer than that default alone would suggest), `fetchNeighborhood` reseeds only a **bounded** window — up to 10 siblings on each side of the drop point, fetched via Prisma cursor pagination (`cursor: {id}, take: ±10`) rather than loading the whole collection — matching the real view order (`sortOrder` asc, `createdAt` desc tiebreak, same as `queries.ts`'s `viewOrder`) so the reseed never silently reshuffles siblings relative to each other beyond resolving the collision. A full-list renumber is never triggered. DnD ships only where `viewOrder` already sorts by `sortOrder` — Inbox, Someday, All, and subtasks (reusing the same `orderingScope` helper, which picks "siblings under the same parent" vs. "my own personal/workspace top-level list" from the dragged task itself) — the computed-order views (Today/Upcoming/Overdue/Scheduled/Delegated/Completed) get no drag handle, consistent with their ordering having no independent meaning to preserve. Reordering inside a filtered subset of an orderable view is well-defined and safe for the same reason the bounded rebalance is: a drag only ever reads/writes the two visible neighbors (and, on collision, their immediate surroundings) — tasks hidden by an active filter are never touched. New dependency: `@dnd-kit/core` + `@dnd-kit/sortable` + `@dnd-kit/utilities`; `KeyboardSensor` gives arrow-key reordering for free.

## 2c. Board, Timeline, Milestones (Phase 3 batch 5)

**Subtask reorder UI carry-over (closed first, before any batch 5 feature work):** `reorderTask`'s service-layer support for subtasks (`orderingScope` picking `{parentId}` when the dragged task has one) shipped and was integration-tested in batch 4, but `TaskSheet`'s subtask list was a plain, unordered `<ul>` with no drag handle at all. A new `SubtaskList` client component (`features/tasks/components/subtask-list.tsx`) wires the identical dnd-kit sensors + optimistic-reorder-then-rollback-on-failure shape `TaskListWithSelection` already uses for Inbox/Someday/All, calling the same `reorderTaskAction`. The drag handle is permission-gated **per subtask**, not inherited from the parent task's own `canEdit` — a subtask can have different assignees than its parent, so `canEditTask` needed evaluating against each subtask's own policy fields. This required two small, additive changes: `canEditTask`/`canDeleteTask` in `tasks/server/access.ts` now take a narrowed `Pick<TaskPolicyRecord, "scope" | "ownerId" | "workspaceId" | "createdById" | "assignees" | "project">` type (`TaskEditPolicyFields`) instead of the full record — every existing caller already passes a full `TaskPolicyRecord`, which trivially satisfies the narrower shape, so this is a pure widening, not a behavior change — and `getTaskDetail`'s subtask `select` grew from `{id, title, status}` to include those same policy fields, with `canEdit: canEditTask(viewer, s)` computed per row.

**Board columns = `ProjectSection`, resolving Q-DM-5 (open since Batch 4's gate doc) as an implementation-detail call rather than inventing a parallel "board status" concept:** a column is a user-named, manually-reorderable grouping — it carries no relationship to `TaskStatus` at all. Dragging a card between columns changes only `Task.sectionId`/`sortOrder`; the checkbox (or the sheet's Complete button) remains the *only* way a task's status changes. A permanent "No column" group (tasks with `sectionId: null`) always renders first and is never itself draggable — it has no underlying `ProjectSection` row to reorder.

- **Server** — `features/projects/server/sections.ts` (new): `createSection`/`renameSection`/`archiveSection`/`reorderSection`/`listSections`, gated by `canEditProject` (no new capability — a column is exactly as editable as its project, the same precedent labels and dependencies already set for object-relationship-gated mutations). `archiveSection` unlinks its tasks (`sectionId → null`) rather than leaving a dangling reference or cascading a delete — consistent with how `archiveMilestone` (below) and the existing soft-delete-everywhere convention treat "remove this grouping" as distinct from "destroy its contents." `reorderSection` is a **third consumer** of `domain/ranking.ts`'s `rankBetween`/`needsRebalance`/`reseedRun` (tasks in Batch 4, board columns here, milestones below) — same pure math, a parallel (not shared) bounded-rebalance wrapper because `ProjectSection` and `Task` are different Prisma models with different delegates, the same reason `sections.ts`'s rebalance loop isn't literally the same function as `tasks/server/service.ts`'s.
- **Card move** — `moveTaskToSection(viewer, taskId, {sectionId, beforeId, afterId})` in `tasks/server/service.ts` handles both a same-column reorder and a cross-column move as one mutation (a drop always lands at a specific position in its destination column). This required a genuine refactor of `reorderTask`'s internals: the bounded-rebalance logic (compute rank from two neighbors, reseed a bounded window on collision) was extracted into a shared `computeRankInScope(tx, scope, excludeId, beforeId, afterId)` that takes an arbitrary `Prisma.TaskWhereInput` scope instead of deriving one from `orderingScope(task)` — `reorderTask` still calls it with the original personal/workspace/subtask scope, unchanged; `moveTaskToSection` calls it with a new `{projectId, sectionId, parentId: null}` scope. **`orderingScope` itself was deliberately left untouched** — it does not know about projects/sections at all, so dragging in Inbox/Someday/All/subtasks (which never touch `sectionId`) is provably unaffected; only the explicitly-new project+section scope is new surface area. Rejects (`NOT_FOUND`): moving a task with no project at all (board moves are project-scoped by construction), and a `sectionId` that belongs to a different project than the task's own (defensive — the client can't reach this via the UI, since a board only ever shows its own project's columns, but a crafted request must still be rejected server-side). Records a `section_changed` task activity, but **only when the column actually changes** (a same-column reorder is silent, matching `reorderTask`'s own "reordering isn't watcher-notable" precedent) — no new notification type, consistent with "do not create a separate Board notification system."
- **Client** — `features/projects/components/board/{board-view,board-card}.tsx`: one `DndContext` per board hosts both column-level reorder and card-level drag, the standard dnd-kit "multiple containers" pattern — `onDragOver` moves a card between columns' local state live (so the destination column's own nested `SortableContext` reflows during the drag itself, not just on drop), `onDragEnd` computes the final neighbor ids and calls `moveTaskToSectionAction`/`reorderSectionAction`. The unsectioned column still participates in the outer columns' `SortableContext` (so cards can be dropped into/out of it) but its own `useSortable` call is permanently `disabled` and renders no handle. `BoardCard` is a new, deliberately compact card component — not a reuse of `TaskRow` — since a kanban card's information density is lower by design (title, due date, priority, a small `PeopleCluster`, up to 2 label chips) per the brief's "do not overdesign task cards."

**Timeline found and closed a real schema-vs-UI gap, not just a rendering task:** `Task.startOn`/`startAt` already existed — modeled, CHECK-constrained (`tasks_start_before_due_check`), and fully handled by `domain/schedule.ts`'s `normalizeSchedule` — but a full grep of the `tasks` feature outside `queries.ts`/`create.ts`/`schedule.ts` itself found **zero** callers that ever set a non-null start date; no action, no schema field, no UI control existed anywhere. Per the batch brief's explicit instruction ("add the smallest correct extension… do not fake timeline duration using only due dates unless explicitly documented as a fallback"), this batch added exactly that extension rather than working around its absence:
- `updateTaskSchema` gained `startOn`/`startTime` (mirroring the existing `dueOn`/`dueTime` shape exactly); `updateTask()`'s schedule-handling block now resolves **both** dates together through one `normalizeSchedule` call (previously due-only), so `startAfterDue`/`startAfterDueTime` validation — already written, previously unreachable — is now live. `TaskSheet` gained a "Start date" field directly above the existing "Due date" one, same date+time pill layout.
- The Timeline view itself is **read-first by design, no drag/resize** — per the brief's own stated preference ("a read-first timeline with safe date editing is better than a fragile Gantt clone"), editing a task's dates still goes through the TaskSheet form; Timeline's own interaction surface is limited to navigation (Prev/Next/Today, ±7 days per click) and clicking a bar/label to open the sheet.
- `getTimelineTasks(viewer, projectId, {from, to}, filters)` windows its query to the visible date range rather than a project's entire history: a task is included only if its start→due span overlaps `[from, to]` at all (computed via two `OR` fragments — excluded only if it *has* a start/due date that falls outside the window on that side — no raw SQL/coalesce needed). Tasks with **neither** date are excluded from the main result and counted separately (`noDateCount`) rather than drawn as a zero-width bar at an arbitrary position — the explicit "tasks without dates handled separately" requirement.
- Rendering (`features/projects/components/timeline/{timeline-view,timeline-row}.tsx`) uses one CSS grid per project: a label column plus one 36px column per visible day. Every cell in a given task's row — the label, each day's background cell, and the task's own bar — carries the **same explicit `gridRow`** (grid auto-placement cannot be trusted to overlap a background cell and a bar into the same cell; only explicit placement on both axes allows that overlap, so this is not optional). The "today marker" is the today-column's cells getting a tinted background across every row, computed once from `compareDates`/`diffDays` against the viewer's own `todayIn(timezone)`.

**Milestones (`features/milestones/`, new feature slice, `{access,service,queries,actions}` — the standard layering):** `Milestone` (`projectId, title, description, dueOn, status: OPEN|COMPLETED, completedAt, sortOrder, createdById, archivedAt`) is editable exactly when its project is (`canEditMilestone` just calls `canEditProject` — no new capability, same precedent as board columns). **Progress (`{done, total}`) and `isOverdue` are always derived at request time** (`getMilestones` groups the milestone's linked tasks by status; `isOverdue` is `status === "OPEN" && dueOn < today`) — never stored, so they can never drift out of sync with the tasks or the calendar. `archiveMilestone` unlinks its tasks (`milestoneId → null`) rather than cascading a delete, same shape as `archiveSection`. `reorderMilestone` is the ranking pattern's third consumer (bounded rebalance against the `Milestone` table). Task↔milestone linking deliberately reuses the **existing** task-update surface instead of a new mutation: `updateTaskSchema` gained `milestoneId` (validated same-project — `milestoneOtherProject` error code — and automatically cleared whenever a task's `projectId` changes, mirroring the existing `sectionId`-clears-on-project-move rule), and `TaskSheet` gained a "Milestone" `<select>` next to the existing "Project" one, populated from `listMilestoneOptions(viewer, task.project?.id)`. Linking/unlinking records a distinct `milestone_changed` task activity (not folded into the generic `"updated"` bucket, matching `schedule_changed`'s precedent) but — consistent with "editing a task shouldn't spam its watchers over every minor field" — triggers no notification.

Icons: `ListTodo`/`Kanban`/`GanttChart`/`Milestone` (lucide-react ships all four literally named for this). Visual baselines (`project`, `board`, both desktop-only since `SubNav` hides `<lg`) re-recorded and reviewed.

## 2d. Storage architecture, attachments, avatars, ownership transfer (Phase 3 batch 6, final batch)

**Storage abstraction (`src/server/storage/`)** — mirrors the `EmailProvider` pattern (D14) exactly: a small interface (`upload`/`download`/`remove` on `StorageProvider`, `provider.ts`) that domain/service code depends on, never a vendor SDK directly.

- **`VercelBlobStorageProvider`** (`vercel-blob.ts`): every object uploaded with `access: "private"` and `addRandomSuffix: true`. A private Blob store requires authentication for *every* read and write at the storage layer itself — not just an unguessable URL — so confidentiality for attachments comes from two independent layers: the store's own access control, and the application-layer visibility check every download route performs regardless.
- **`InMemoryStorageProvider`** (`memory.ts`): the dev/test default, an in-process `Map`. Unlike `ConsoleEmailProvider` (which just logs and discards), this one actually round-trips bytes — tests upload, then read back what they uploaded — because attachment/avatar tests need that.
- **`UnconfiguredStorageProvider`**: thrown lazily, only when something actually tries to use storage, never at import time (same reasoning as the email provider: a production deploy with no store connected yet still builds and serves every other route).
- **Selection** (`index.ts`): credentials present (`BLOB_READ_WRITE_TOKEN`, or OIDC via `VERCEL_OIDC_TOKEN`+`BLOB_STORE_ID`) → real adapter. No credentials + `process.env.VERCEL_ENV` set (a genuine Vercel deployment) → `Unconfigured`. No credentials + no `VERCEL_ENV` → in-memory. **Deliberately not `NODE_ENV === "production"`** — `next start` (E2E's own webServer runs one, same as a developer's local production build) also sets that, and must still work with no Blob store at hand, the same way E2E already forces `EMAIL_PROVIDER=console` against a production build regardless of `NODE_ENV`.
- **A real bug found via E2E, not a hypothetical:** the provider instance was originally a plain module-level `let`. Under `next start`, uploading an avatar through a Server Action and then loading it through the `/api/avatars/[userId]` Route Handler produced a 404 with no thrown error anywhere — Next.js had bundled the action and the route into separate chunks, each evaluating its own fresh copy of the module, so the two `instance` variables (and their two separate in-memory `Map`s) never saw each other's writes. Fixed by caching the instance on `globalThis`, the exact trick `src/server/db.ts` already uses for the same underlying class of problem (surviving multiple module evaluations within one process) — confirmed by a direct test (`storage provider (unit)` in `batch6.integration.test.ts`) and by the E2E avatar flow passing end-to-end afterward. In real production this specific failure mode can't occur (Vercel Blob is external, not in-process), but the `globalThis` fix is correct regardless and costs nothing.

**Attachments (`features/attachments/`, new feature slice — `{domain/validation.ts, server/{access,service,actions}.ts}`, plus `types.ts`):**

- **Model**: `Attachment(id, taskId, workspaceId?, uploadedById, filename, mimeType, size, storageKey, createdAt, deletedAt?)`. `storageKey` — the provider's handle, never its URL — is what `src/server/storage` uses to fetch/remove the bytes; the row itself is the metadata record (§39: "metadata is separate from the storage provider"), not a cache of something the provider already tells you.
- **Permissions**: upload requires `canEditTask` (the same gate checklist items and subtasks already use); delete requires the uploader **or** `canDeleteTask` — the identical shape `deleteComment` established in batch 2 (`comment.authorId === viewer.user.id || canDeleteTask(viewer, task)`), reused verbatim rather than inventing a new rule. Visibility (including download) follows the task's own visibility — anyone who can see the task can see and download its attachments, matching how comments already behave.
- **Validation** (`domain/validation.ts`, pure, no I/O): a 20 MB limit; an explicit MIME **allowlist** (images, PDF, plain text/CSV/JSON, zip, common Office formats) rather than a denylist; a dangerous-extension blocklist (`.exe`, `.bat`, `.sh`, `.jar`, …) checked against the filename regardless of claimed MIME type; and a magic-byte sniff (Windows PE "MZ", ELF, Mach-O, shebang `#!`) checked against the actual uploaded bytes, independent of both the filename and the claimed MIME type — a renamed executable claiming to be `notes.txt` with `text/plain` is still rejected. The same `checkFile` primitive is reused (not re-implemented) by avatar validation with its own limit/allowlist, so the dangerous-extension/signature logic exists in exactly one place.
- **Upload failure handling**: Blob upload happens first; if the subsequent DB insert fails, the just-uploaded Blob object is deleted (compensating cleanup, not a distributed transaction) so nothing is ever orphaned by a failed *upload*. If the Blob upload itself fails, nothing has been written to the DB yet — there's nothing to compensate.
- **Delete handling**: the DB row is soft-deleted (`deletedAt`) inside a transaction with its `attachment_removed` activity record, so the audit trail ("who uploaded what, when") survives even though the file is also gone; the underlying Blob object is then best-effort removed (failure here only logs — the DB row, the source of truth for "does this attachment exist," is already correctly updated, so a failed Blob delete produces an orphaned object, never a half-removed attachment users can still see).
- **Lifecycle**: a task's own soft-delete (`deletedAt`) already excludes it from `findVisibleTask`'s results — since every attachment operation loads its task through that same function, attachments on a soft-deleted task become unreachable automatically (no special-case code needed) and reachable again the moment the task is restored, mirroring the Reminder lifecycle precedent from batch 3 (§2a above) exactly. Task **hard**-delete and workspace hard-delete don't exist anywhere in the product yet (only soft-delete/archive) — `Attachment.taskId`/`workspaceId` are `onDelete: Cascade` defensively, but **whoever eventually builds a real purge job (Phase 4+) must also call `storageProvider.remove()` for each attachment's `storageKey` before/alongside that hard-delete**, or Postgres's cascade will silently orphan the Blob objects with no DB row left pointing at them to clean up later. Flagged here so it isn't rediscovered the hard way.
- **Download route** (`src/app/api/attachments/[attachmentId]/route.ts`): checks `getSessionUser()` (not `getViewer()`, which calls `requireUser()` → `redirect()` — valid inside the render/action pipeline, not inside a bare Route Handler) for a clean 401, then re-derives the caller's task visibility via the normal service call on **every single request** — the id is a cuid, not a secret, so nothing about this route trusts "they got this far before" as a substitute for a real check.
- **UI**: `AttachmentsSection` (new, in `TaskSheet`, inserted after the checklist section) — a hidden file input behind a compact "Add a file" label, a list of `{filename, size, download link, delete button}` rows, optimistic add/remove with rollback on failure. Upload goes through `FormData` (not the usual Zod-validated JSON action shape) because a browser `File` object has no meaningful Zod schema; the real validation happens server-side against the actual bytes regardless of what the client claims.
- **Activity**: `attachment_added`/`attachment_removed`, both `entityType: "task"` (no new entity type — follows the `section_changed`/`milestone_changed` precedent of hanging sub-events off their parent task). No notification — the brief's own steer ("no notification unless the existing watcher policy strongly justifies it") didn't find a justification, and none of batches 1–5 added a notification for a similarly low-urgency event (e.g. labels changing) either.

**Avatars (`features/account/`, extended, reusing the same storage abstraction):**

- `User` gained `avatarStorageKey`/`avatarMimeType` (new nullable columns); `avatarUrl`'s *meaning* changed from "an external URL" to "our own stable `/api/avatars/[userId]` path, or null" — a derived value, never touched directly except by `setAvatar`/`removeAvatar`. Every existing `avatarUrl` reader (the `Avatar` component, every `PersonRef`-shaped query across tasks/workspace/collaboration) already treats it as an opaque nullable string handed straight to `<img src>`, so this redefinition needed zero changes anywhere else in the codebase — confirmed by grep before relying on it.
- **Deliberately not task-attachment-style scoped**: `/api/attachments/[id]` re-derives full task visibility per request because attachments are real, potentially sensitive user documents. Avatars are profile photos rendered broadly across shared contexts (assignee lists, comments, the team directory, the account menu) — `/api/avatars/[userId]` only checks that the caller is signed in at all, not a per-viewer visibility computation against the pictured user. The Blob store is still private either way (never a raw guessable URL), but this is a conscious, narrower authorization decision than attachments get, made explicitly rather than by accident — documented in `docs/ARCHITECTURE.md`'s new "File storage" section per the brief's own requirement to state this choice outright ("if avatars are public-readable, say so; otherwise use signed/controlled access" — this is the controlled-access option, deliberately scoped wide).
- **Replace**: uploads the new object, updates the DB row to point at it, *then* removes the previous Blob object — in that order, so a failure cleaning up the old object never leaves the user without a working avatar (worst case: one orphaned object, never a broken one).
- **Validation** (`features/account/domain/avatar.ts`): reuses `checkFile` from the attachments domain module (not a second implementation) with its own 5 MB limit and an image-only MIME allowlist (PNG/JPEG/WEBP/GIF).
- **UI**: `AvatarForm` in `features/account/components/settings-forms.tsx` (new, alongside the existing `ProfileForm`/`AppearanceForm`/etc. in the same file) — avatar preview + "Upload photo"/"Remove" controls, wired into `/settings/profile` above the existing Name field.

**Transfer ownership (`features/workspace/`, extended):**

- **A dedicated `transferOwnership(viewer, {workspaceId, userId})` service function — explicitly not two `changeMemberRole` calls.** Both role updates (target → OWNER, caller → ADMIN) happen inside one `db.$transaction`, so the workspace can never be *observed* with zero or two owners, even under a crash mid-operation — a swap, by construction, can't change the owner count, so no last-owner *count* check is structurally needed (a defensive `count === 1` assertion still runs after both updates, non-load-bearing, catching a logic error rather than a race).
- **Guards**: only the current OWNER may call it (checked against the *request's own* `viewer`, same staleness characteristics every other capability check in this codebase already has — no new risk introduced); rejects transferring to self, to a non-member, to a GUEST, or across workspaces (the `{workspaceId, userId}` composite key makes a cross-workspace target structurally unreachable, not just checked). All of these are integration-tested explicitly (`batch6.integration.test.ts`'s "ownership transfer" block), including a test that the *new* owner's fresh capabilities (re-fetched via a new `getViewer()` call, not reused from before the transfer) actually let them act as owner immediately — proving the capability model picked up the swap, not just the raw DB row.
- **UI**: a new "Transfer ownership" item in `MemberActions`' existing dropdown (shown only when the viewer is OWNER and the target is an eligible active, non-GUEST, non-self member — precomputed server-side in `listMembers` as `canTransferOwnershipTo`, same "the UI only ever offers what the server will accept" precedent `assignableRoles` already set) with its own `ConfirmDialog` (explicit confirmation, per the brief's "not a simple role edit" instruction) — a separate dropdown action and dialog, not folded into the existing role `<select>`.
- **Notification**: one additive `NotificationType` (`WORKSPACE_OWNERSHIP_TRANSFERRED`), sent to the new owner only, inside the same transaction as the role swap.

**A real, pre-existing bug found and fixed while building this batch's own E2E coverage (not introduced by this batch):** every row in `/team`'s and `/team/guests`'s member list mounts with an `animate-rise` entrance animation. Per the CSS spec, any element whose keyframes touch `opacity` or `transform` becomes its own stacking context — so each `<li>` row was *already*, silently, its own stacking context before this batch touched anything. That traps a row's `MemberActions` dropdown (`z-index: 40`) inside its *own* row's stacking context; a later sibling row (also its own stacking context, ranked purely by DOM order since neither has an explicit z-index at the row level) paints over it regardless of that nested z-index. Net effect: a dropdown action on any row except the last was genuinely unclickable at the coordinates a real click — or Playwright — would use. This affected the pre-existing Remove/Deactivate items identically; nothing before this batch had ever clicked a `MemberActions` item against a multi-row seeded list in an automated test to catch it (existing coverage only exercised the role `<select>`, or single-row flows). Diagnosed with `document.elementFromPoint` at the target button's own bounding-box center (not just "it eventually worked"), fixed at the row level — `relative` + `has-[details[open]]:z-10` on the `<li>` in both `team/page.tsx` and `team/guests/page.tsx` — rather than inside the shared `MemberActions`/`ConfirmDialog` components, since the stacking-context trap is a property of *where* the dropdown is mounted, not of the dropdown itself.

**A seeded-fixture trap, worth remembering for future E2E work:** the first attempt at the ownership-transfer flow targeted the seeded showcase workspace (`e2e/support/fixtures-data.ts`) directly. It failed silently — the UI just didn't update after confirming — because showcase fixture ids (`e2e_ws_en_light`, etc.) are hand-assigned strings, not real Prisma `cuid()`s, and **every** action's `z.cuid()` input validation (not new to this batch — `removeMemberAction`/`deactivateMemberAction` already shared the same `memberSchema`) rejects them, returning `invalidInput` with nothing thrown to notice. No existing flow spec had tripped this because every prior showcase-fixture test only *reads* that data (visual baselines, `people.spec.ts`). The fixed flow creates its own fresh workspace through the UI instead (real CUIDs) and inserts a second member directly via `pg` (mirroring `seed.ts`'s own raw-SQL approach) rather than through the email-invite flow, which E2E has no way to read a token back from (the same reason `invitations.spec.ts` only covers send/list/revoke, never accept).

**One migration** (`phase3_batch6_attachments_ownership`): `Attachment` table; `WORKSPACE_OWNERSHIP_TRANSFERRED` added to `NotificationType`; `User.avatarStorageKey`/`avatarMimeType` columns.

**New dependency:** `@vercel/blob` (^2.3 — the minimum version with private-store support).

**`next.config.ts`** gained `experimental.serverActions.bodySizeLimit: "22mb"` (default 1 MB) — attachment (20 MB) and avatar (5 MB) uploads both go through Server Actions as `FormData`, which needs headroom above the larger limit plus encoding overhead.

**Tests:** `src/server/__tests__/batch6.integration.test.ts` (27 cases) — a DB-independent `storage provider (unit)` block (upload→download round-trip, missing-key download, idempotent remove); attachment upload/metadata/activity, upload permission rejection, cross-workspace access rejection, empty-file/oversized/disallowed-MIME/renamed-executable rejection, delete permission (uploader vs. non-uploader), double-delete rejection, task-soft-delete-hides-then-restore-reveals; avatar upload/replace/remove, idempotent double-remove, oversized/wrong-MIME rejection, per-user isolation; ownership transfer success (exactly-one-owner invariant, audit, notification), non-owner/self/non-member/GUEST/cross-workspace rejection, post-transfer capability refresh; board-section rename permission (the one coverage gap left over from batch 5, which only tested archive). `e2e/planner-batch6.spec.ts` (5 flows): attachment upload → download → delete persists after reload; disallowed file type shows a visible error; avatar upload → remove; workspace ownership transfer (against a freshly-created workspace, not the showcase fixture — see above); board column rename → delete. ## 4. How to work here (rules agreed with the product owner)

1. **Phase discipline:** before any major phase, run the **pre-implementation gate** (`docs/PHASE_PLAN.md` §4) and write `docs/phases/PHASE_<n>.md`. Implement only the approved phase, stop, and report.
2. **Definition of Done** (`docs/ACCEPTANCE_CRITERIA.md` D1–D24):
   - Server-side authorization; Zod validation; tenant scoping.
   - Loading, empty, error, permission and archived states; mobile and RTL checked.
   - Tests added; typecheck, lint, tests, build and E2E all green.
   - **Docs and coverage matrix updated.**
3. **Layering:** `actions.ts` (validate → `getViewer()` → service → `runAction`) → `service.ts` (business rules, transactions, audit) → `access.ts` (object permissions) → domain (pure, unit-tested). No DB access or business logic in actions. Services are **language-neutral** and throw `DomainError(code)`.
4. **§91 shared services:** every task insert goes through `src/features/tasks/server/create.ts` (`createTask`); never add a second insert path. Activity and audit go through `src/server/activity.ts`.
5. **i18n is mandatory for every change:**
   - every string goes into `messages/en/*.json` **and** `messages/fa/*.json`, with semantic keys and ICU plurals
   - logical CSS only (`ms/me/ps/pe/start/end`); mirror directional icons; `dir="auto"` on user content
   - format numbers and dates with `useFormat`/`getFormat`
   - Quick Add parsing stays English-only (I18N-12)
6. **People:** any small group of users uses `PeopleCluster` (DESIGN_SYSTEM §13). Never hand-roll avatar rows; never bring back `AvatarGroup`.
7. **Design:**
   - Follow `docs/DESIGN_SYSTEM.md` and the references; pages without a reference are composed from existing patterns (§96).
   - Panel header = title at the start, selectable pills **centred**, actions at the end.
   - Forms are **single column, labels at the start**, white pill fields, and dialog footers with two equal buttons (§14).
   - `cn()` does not resolve Tailwind conflicts: set sizes on wrappers, not by overriding a primitive's classes.
8. **Regression rule (§90):** before changing a shared component, check COMPONENT_INVENTORY "Used by" and re-run the affected flows. After intentional UI changes, re-record and **review** the visual baselines.
9. **Next.js 16 is newer than your training data:** read `node_modules/next/dist/docs/` before using an API (`AGENTS.md`). `proxy.ts` replaces middleware; request APIs are async.
10. **Don't touch the owner's running `npm run dev`:** E2E builds into `.next-e2e`, and you must not delete `.next` while their dev server runs.
11. Commit or push only when asked. Commit messages end with the co-author trailer the harness provides.

## 5. Setting up on a new machine

Requirements: **Node 22+** and npm. No Docker, no local database — the database is always a hosted Neon Postgres branch (see `docs/ARCHITECTURE.md` → "Database (Neon)"). Ask whoever manages the Neon project for a connection string to the **Development** branch (or create your own personal branch from it).

```bash
git clone https://github.com/mehranr1990/planner.git
cd planner
# copy the reference/ folder here manually (not in git)
npm install                      # runs `prisma generate` (client goes to src/generated, git-ignored)
cp .env.example .env             # fill in DATABASE_URL + DIRECT_URL for your Neon Development branch
npm run db:deploy                # applies prisma/migrations (via DIRECT_URL)
npm run dev                      # http://localhost:3000
```

Checks:

```bash
npm run typecheck && npm run lint && npm test && npm run build
npx playwright install chromium  # if the CDN is blocked (it was, from Iran — HTTP 403), skip it and use PW_CHANNEL
PW_CHANNEL=msedge npm run test:e2e        # or PW_CHANNEL=chrome; 32 flows
PW_CHANNEL=msedge npm run test:visual     # 25 screenshots
```

Point `DATABASE_URL` at a **disposable** branch for E2E (it deletes and recreates `@e2e.local`/`@e2e.test` fixtures) — not your personal Development branch, and never Production. `playwright.config.ts` sets `APP_ENV=test` automatically for local runs; the seeding step refuses to run without it.

**Visual baselines are per platform and browser** (`e2e/__screenshots__/<platform>-<browser>/`). Only `win32-msedge` is committed. On another OS or browser, run `npm run test:visual:update` once, **review the images**, and commit them as that platform's baseline. CI (`.github/workflows/ci.yml`) runs on `ubuntu-latest`/chromium and does not yet run `test:visual` for the same reason — a `linux-chromium` baseline needs generating once from that runner before it can be enabled there.

### Known pitfalls

- **Prisma is pinned to 7.10.0:** npm `latest` pointed at an 8.0 RC. Prisma 7 needs `prisma.config.ts` and the `@prisma/adapter-pg` driver adapter.
- **`DATABASE_URL` vs `DIRECT_URL`:** the app runtime only ever uses `DATABASE_URL` (Neon's pooled endpoint); `prisma.config.ts` (migrations, `prisma studio`) only ever uses `DIRECT_URL`/`DATABASE_URL_UNPOOLED` (unpooled). There is no fallback between them — the CLI fails with a clear error if the direct one is missing, rather than silently migrating through the pooler. `prisma generate` needs neither (it never connects).
- **Never set a manual `DIRECT_URL` scoped to Vercel Preview** (or at all, ideally) — it would override the Neon integration's per-deployment `DATABASE_URL_UNPOOLED` and point every Preview's migrations at the wrong branch. See `docs/ARCHITECTURE.md`.
- **Turbopack ignores `adjustFontFallback: false`.** The explicit font stack in `src/app/layout.tsx` exists because of this; don't "simplify" it back to the font variables.
- **Native date/time inputs** follow the browser's locale; dates are stored and shown in Gregorian (Jalali is Q-I18N-1).
- **The seed only touches e2e accounts:** E2E global setup deletes and recreates `@e2e.local` / `@e2e.test` accounts only, and refuses to run at all without `APP_ENV=test` or against `VERCEL_ENV=production`.
- **Email provider defaults to Resend under `next start`** (`NODE_ENV=production`), which throws if `RESEND_API_KEY`/`EMAIL_FROM` aren't set. The provider is built lazily (only on first actual send), so this never breaks `next build`'s page-data collection — but set `EMAIL_PROVIDER=console` in your env (already done for E2E's `webServer`, `playwright.config.ts`, and CI) if you run a local production build without Resend credentials and plan to exercise invite/reset flows.
- **PGlite is gone (2026-10).** If you see references to it in old regression-log entries (`docs/QA.md` §3c/3e) or git history, that's historical — it described a local-only workflow this project no longer uses.
- **Local `prisma dev` daemon flakiness (seen in Phase 3 batches 2–5 — the single most recurring friction point across every batch so far):** under heavy sequential load (the full `vitest` integration suite, or several Playwright runs back to back — and batch 5's own verification needed ~4 restarts across one session) the daemon can start dropping connections ("Connection terminated unexpectedly" / "Server has closed the connection"), on files it had nothing to do with. Fix: kill it, clear its lock files, start it again —
  ```bash
  PID=$(netstat -ano | grep LISTENING | grep <port> | awk '{print $5}' | head -1); taskkill //F //PID "$PID"
  rm -rf "$LOCALAPPDATA/prisma-dev-nodejs/Data/durable-streams/<project>/server.lock" "$LOCALAPPDATA/prisma-dev-nodejs/Data/durable-streams/<project>/server.lock.lock"
  npx prisma dev &   # note the new port it prints and update .env's DATABASE_URL/DIRECT_URL if it changed
  ```
  **The lock is a directory** (`server.lock`, plus its own `proper-lockfile`-internal `server.lock.lock` — both under `durable-streams/<project>/`, not `Data/<project>/.lock` as that path alone suggests; confirmed batch 5), so `rm -f` silently no-ops on it (`rm: cannot remove '…': Is a directory`) without `-r` — if a restart still reports "Lock file is already being held" after an `rm -f`, that's why. **Never delete `Data/<project>/` itself** (only the two `server.lock*` paths above) — it holds the real data (`Data/<project>/.pglite/`, `durable-streams/<project>/durable-streams.sqlite*`), and wiping it means reapplying every migration (`npx prisma migrate deploy`) before tests pass again (happened once, in batch 4, recovered with no lasting harm since this instance only ever holds disposable fixtures — but still a needless detour). A quick health check before trusting a restarted daemon: `select 1` through a raw `pg` client, or just rerun one test file — `netstat` showing the port LISTENING is not proof the daemon is actually answering queries. Not seen against a real Neon branch — don't spend time hardening this further, just restart it.
- **A stale/partial `next build` output can poison subsequent builds** (seen once in batch 3): deleting `.next` or `.next-e2e` mid-build and letting Turbopack retry against the partial result produced a spurious `next/font/google` resolution error on every later attempt. If a build fails strangely and you can't explain it from the diff, delete the dist dir (`.next` or `.next-e2e`) fully and rebuild from scratch before assuming it's a real regression.
