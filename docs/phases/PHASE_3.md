## E. Permission model for new mutations (no new capabilities needed)

Confirmed by re-reading `capabilities.ts`: `tasks.assign` already exists and is granted to OWNER/ADMIN/MANAGER/MEMBER. `canAssignTask` (`tasks/server/access.ts`) already combines it with `canEditTask` and is unused today — Phase 3 is its first caller, unchanged. Watchers, labels, subtasks, and comments need **no new capability** — they're gated by the existing object-relationship rule (`canEditTask`/`findVisibleTask`), consistent with PERMISSIONS.md §2 having zero Phase-3-tagged capability rows. Label creation requires `tasks.create` in that context (same gate as creating a task there); rename/archive requires the creator or `workspace.manage` (a judgment call, documented here rather than invented silently — labels are shared workspace taxonomy, so arbitrary members shouldn't be able to delete labels others depend on, but anyone who can make tasks there can make labels there).

## F. Technical notes (implementation decisions, not product decisions)

- **Assignee/label changes are "set" operations**, not individual add/remove calls — `setTaskAssignees(viewer, taskId, userIds)` / `setTaskLabels(viewer, taskId, labelIds)` diff old vs. new server-side and emit one activity event with `{added, removed}`, matching how the existing `PeoplePicker.onChange` already hands back a full next-selection array. Neither is version-guarded (`task.version`) — they're relation changes, not field overwrites, consistent with how `addDependency`/`addChecklistItem` already behave.
- **Watching is self-service and visibility-gated only** (not edit-gated) — anyone who can see a task can watch it; nobody can make someone else watch something.
- **Activity `entityType` stays `"task"`** for all task-scoped sub-events (assignees, watchers, subtasks, labels), with details in `data`, exactly matching the existing `dependency_added` precedent — no union-type widening needed in `src/server/activity.ts`.
- **`TASK_ASSIGNED` notification** fires on `setTaskAssignees` for newly-added assignees only (never for self-assignment, never for removed assignees).
- **Subtask creation** reuses `createTask` (§91) via a new `"SUBTASK"` `TaskSource` literal (additive to the existing union) — no second insert path.
- A new `src/features/labels/` feature (access/service/actions/queries) holds label CRUD; `tasks/server/service.ts` calls into it for `setTaskLabels`, keeping label-the-entity and label-the-relation cleanly separated (and ready for Project tagging later, once Q-DM-2 resolves — not attempted now, since `Project` has no label relation today and inventing one isn't in this batch's approved scope).

## 13. Batch completion notes (added as each batch finishes; full detail lives in `docs/HANDOFF.md` §2/§2a)

- **Batch 1** (assignees, watchers, subtasks, labels, delegated view): shipped as planned in §D, zero deviations. See `docs/HANDOFF.md` §2.
- **Batch 2** (dependencies UI, comments, mentions): shipped as planned, plus one deviation — the product owner asked for live mention autocomplete directly in the batch 2 brief, superseding this gate doc's §D note ("no live search-while-typing autocomplete yet"). See `docs/HANDOFF.md` §2.
- **Batch 3** (reminders, notification execution + inbox, activity hardening): shipped with two deviations from this gate doc's original batch plan (§D): **attachments were listed under batch 3 here but were explicitly excluded by the batch 3 brief** (still unscheduled — needs a decision on which batch picks it up); and **reminder delivery shipped in batch 3 too**, not deferred to Phase 4 as §D originally scoped it — done narrowly (a dedicated `Reminder` table + Vercel Cron route), not by building out the Phase 4 `Job` table early. This also resolves Q-PO-13 for this one use case (Cron + an idempotent DB claim), without closing that question for Phase 4's other, more varied consumers. Full design, the due-date-interaction policy table, and the watcher-notification policy are in `docs/HANDOFF.md` §2a.
- **Batch 4** (advanced filters, bulk actions, drag & drop): shipped with scope deviations from this gate doc's original §D line, all deliberate and documented at approval time rather than invented silently:
  - **Board-column reorder deferred to Batch 5.** §D's "drag & drop (task order, board columns, subtask reorder)" bundled board columns in; the product owner's batch 4 brief explicitly excluded Board/Timeline from this batch, and there is no Board UI yet for a column to belong to. Task-order and subtask-order DnD shipped; `ProjectSection.sortOrder` (already in the schema) is untouched and ready for Batch 5.
  - **The `area` filter dimension was dropped** from the originally-requested filter set (assignee, creator, status, priority, label, due date, overdue, project, area, completed, delegated, watched). A full-codebase audit found `Area` has **zero creation/assignment UI anywhere in the product** — no screen can set `Task.areaId` or `Project.areaId` — so an area filter would offer an always-empty picker over an always-null column. Revisit once an Area module ships (Phase 5+); the `PlannerFilters` shape and `plannerFiltersWhere` are structured so adding it later is one more fragment, not a redesign.
  - **`SavedView` stays unused.** §D flagged "Maybe (saved-view reuse of existing `SavedView`)" for schema; the approved brief's URL-persisted filter state (shareable/bookmarkable via `?priority=&label=…`) satisfies "filters survive navigation" without needing saved presets. The model remains schema-only, ready for a future "save this filter combination" feature.
  - **Bulk-mutation permission model: best-effort/partial, not atomic**, decided per the product owner's explicit discretion ("atomic, or partial with documented per-item results") — every `server/bulk.ts` function individually checks `canEditTask`/`canDeleteTask` per requested task (never a batch-wide gate), silently skips ones the caller can't touch, and returns `{updatedIds, skippedIds}` so the UI reports "updated N, skipped M." Chosen over all-or-nothing because `COVERAGE_MATRIX.md`'s PLN-18 row already specified "edit per item," and one locked task in a broad multi-select shouldn't block every other legitimate update. Bulk mutations are **not** optimistic-concurrency (`version`) guarded, the same precedent `setTaskAssignees`/`setTaskLabels` already set for relation-changing (not field-overwriting) operations — manual drag-reorder, a single-task op, stays version-guarded like every other single-task mutation.
  - **Bulk notifications are aggregated per recipient**, per an approved adjustment to the original plan: a bulk action's per-task notification candidates are collected (reusing the exact same single-task notify calls `updateTask`/`setTaskCompletion`/`setTaskAssignees` already make) and, only when a recipient would otherwise receive more than one notification of the same type from one bulk call, collapsed into a single `..._BULK`-typed notification (`src/server/notify-bulk.ts`; 4 new additive `NotificationType` values + a `Notification.data` JSON column for `{count, taskIds}`). A recipient touched exactly once keeps the identical single-task notification, unchanged. Verified with dedicated integration tests enforcing: single-task action → single non-bulk notification; bulk-of-one → identical to single-task (no behavior change); bulk-of-many → exactly one bulk notification per recipient/type; no duplicates; actor always excluded; a user without visibility is never notified.
  - **Ordering reuses the existing `Task.sortOrder` Float column** (already present, already used for project-list ordering) — no new ordering field. `reorderTask` computes the new fractional rank entirely server-side, inside one transaction, from the two neighbor ids the client's own optimistic reorder supplies; per the approved adjustment, a rank collision triggers a reseed of only a *bounded* neighborhood (±10 siblings around the drop point, fetched via cursor pagination) rather than the whole collection, and a full-list renumber is never triggered. DnD ships only for the views `queries.ts`'s `viewOrder` already sorts by `sortOrder` — Inbox, Someday, All, and subtasks — not the computed-order views (Today/Upcoming/Overdue/Scheduled/Delegated/Completed), where reordering has no defined meaning.
  - Two new indexes (`Task` on `[ownerId, scope, sortOrder]` and `[workspaceId, sortOrder]`) keep the now-more-heavily-used `sortOrder` ordering fast; no other schema changes. Full design detail, the watcher-notification policy extension, and the data-model note live in `docs/HANDOFF.md` §2b.
